# II-only Vault protocol

The authoritative wire API is [vault.did](../../crates/vault_canister/vault.did). The browser uses the generated [Vault contracts](../../packages/vault-candid/index.d.ts) and [VaultClient](../../packages/vault-client/src/api.ts). Legacy owner methods bind the authenticated IC caller to its own Vaults. Shared methods look up the recorded owner by Vault ID, check the caller’s role and use the recorded owner for v3 encryption and billing. Both protocols use the same existing document format. See the [shared wire contract](team-access.md).

Creation accepts only a 16-byte operation ID. The server allocates a never-reused 16-byte Vault ID from its persistent positive operation serial (zero-extended big-endian u128). It pins a 32-byte random nonce and the vetKD public key in the header. Retry the same operation after an uncertain response; pending creation and completed receipts preserve the assigned identity. Key acquisition accepts that Vault, a 16-byte operation and 48-byte transport public key. Retry with the same transport secret/public pair. The client checks the authenticated current header, the vetted network master key, reply input/public key and decrypted vetKey before deriving the root.

The vetKD context is `kinic-vault/ii-only/v1`. Its input concatenates five fields, each prefixed by an unsigned 32-bit big-endian byte length: raw canister principal, raw owner principal, 16-byte Vault ID, 32-byte nonce and UTF-8 key name. The 32-byte symmetric root uses `kinic-vault/root/v3`. The document AES-GCM associated data is six length-prefixed fields: `kinic-vault/document/v3`, the complete vetKD input, 16-byte object ID, 64-bit big-endian revision, usage string and 32-bit big-endian chunk index. Only document format 3 is supported. Encrypted metadata contains `{ metadata, plaintext_length, chunk_count }`; authenticated extent must agree with the manifest, chunk/hash/nonce counts and final plaintext length. There is no legacy metadata reader.

Listing decrypts metadata only and never reads note chunks. The browser filters titles as you type. “Search note contents” explicitly reads eligible notes sequentially and returns matching object IDs; plaintext is transient and no full-text index or cache is retained. Results match titles OR body IDs and are discarded on query/list changes, lock, Vault/client switch or unmount.

`mutate({operation,action})` atomically stores each successful effect, request digest and reply. Same operation/payload replays for 24 hours; changed payload under the same operation conflicts. Actions include BeginRevision, PutChunk, CommitRevision, DeleteObject, PurgeObject, CancelUpload, DeleteVault and Collect. BeginRevision's inner operation is the upload ID; it differs from the outer mutation operation. Prepaid admission reserves completion receipts and capacity. Unknown network outcomes must be reconciled or retried with their original IDs. Ordinary request replay lives in `operations`; upload-ID reconciliation lives in typed `upload_outcomes` and cannot interpret an ordinary delete result as a committed upload.

Ordinary deletion appends a tombstone and retains accessible history. Purge hides all history and leaves a permanent object fence while bounded GC reclaims ciphertext. CancelUpload preserves one job across batches; DeleteVault physically removes the Vault row after bounded cleanup. There is no permanent Vault tombstone. The three-Vault owner limit includes Pending and Deleting rows; completed deletion restores capacity. Financial journals and operation receipts retain their independent lifetimes; after the final receipt expires a missing Vault returns NotFound. Cleanup uses authenticated owner access and remains available at zero balance. Exact replay and terminal/no-work semantics are tested against real Wasm.

The header binds canister/owner/Vault/nonce/key name/public key, while sequence is mutable. Switching context invalidates pending key attempts, roots and private callbacks. Browser Session guards are local lifecycle protection; ordinary logout cannot revoke a retained session signing key with its still-valid II delegation. See [operations](operations.md) for trust and expiry limits and [validation](validation.md) for reproducible evidence.

## Wiki references and the picker

A standalone paragraph with the exact Markdown spelling `[非公開資料](https://vault.kinic.xyz/embed/<vault-id>/<object-id>)` identifies a private document. Each ID is 16 bytes encoded as 32 lowercase hexadecimal digits. The Wiki article, history and static output contain the reference. Its generic label carries no document metadata.

The Wiki editor opens the trusted Vault origin at `/pick`. The picker sends `{"type":"kinic-vault-picker-ready"}`, and the editor replies with `{"type":"kinic-vault-picker-connect"}`. Each side checks the exact window and origin. Once the user selects an accessible document, Vault rechecks access and sends `{"type":"kinic-vault-selection","vault":"<vault-id>","object":"<object-id>"}`. The editor appends the reference to the current draft.

The interactive preview creates a Vault-origin iframe on an explicit open. Vault obtains its own II delegation, checks current authorization, derives the owner-bound root and renders the document. Credential details require a reveal action and attachments require a download action. If iframe sign-in is unavailable, the frame offers top-level Vault sign-in and a retry.
