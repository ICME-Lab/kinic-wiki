# II-only Vault protocol

The authoritative wire API is [vault.did](../../crates/vault_canister/vault.did). The browser uses the generated [Vault contracts](../../packages/vault-candid/index.d.ts) and [VaultClient](../../packages/vault-client/src/api.ts). Private methods derive owner from the authenticated IC caller; there is no client-supplied owner, application grant, application signature or extra Vault WebAuthn factor.

Creation accepts 16-byte Vault and operation IDs. It pins a 32-byte random nonce and the vetKD public key in the header. Retry the same pair after an uncertain response. Key acquisition accepts that Vault, a 16-byte operation and 48-byte transport public key. Retry with the same transport secret/public pair. The client checks the authenticated current header, the vetted network master key, reply input/public key and decrypted vetKey before deriving the root.

The vetKD context is `kinic-vault/ii-only/v1`. Its input concatenates five fields, each prefixed by an unsigned 32-bit big-endian byte length: raw canister principal, raw owner principal, 16-byte Vault ID, 32-byte nonce and UTF-8 key name. The 32-byte symmetric root uses `kinic-vault/root/v3`. The document AES-GCM associated data is six length-prefixed fields: `kinic-vault/document/v3`, the complete vetKD input, 16-byte object ID, 64-bit big-endian revision, usage string and 32-bit big-endian chunk index. Only document format 3 is supported.

`mutate({operation,action})` atomically stores each successful effect, request digest and reply. Same operation/payload replays for 24 hours; changed payload under the same operation conflicts. Actions include BeginRevision, PutChunk, CommitRevision, DeleteObject, PurgeObject, CancelUpload, DeleteVault and Collect. BeginRevision's inner operation is the upload ID; it differs from the outer mutation operation. Prepaid admission reserves completion receipts and capacity. Unknown network outcomes must be reconciled or retried with their original IDs. Ordinary request replay lives in `operations`; upload-ID reconciliation lives in typed `upload_outcomes` and cannot interpret an ordinary delete result as a committed upload.

Ordinary deletion appends a tombstone and retains accessible history. Purge hides all history and leaves a permanent object fence while bounded GC reclaims ciphertext. CancelUpload preserves one job across batches; DeleteVault ends in a permanent Deleted header. Cleanup uses authenticated owner access and remains available at zero balance. Exact replay and terminal/no-work semantics are tested against real Wasm.

The header binds canister/owner/Vault/nonce/key name/public key, while sequence is mutable. Switching context invalidates pending key attempts, roots and private callbacks. Browser Session guards are local lifecycle protection; ordinary logout cannot revoke a retained session signing key with its still-valid II delegation. See [operations](operations.md) for trust and expiry limits and [validation](validation.md) for reproducible evidence.
