# Standalone II-only Vault operations

Sign in with Internet Identity, then create or select a Vault. There is no additional Vault passkey, recovery secret, backup, import or export protocol. Losing access to Internet Identity permanently loses Vault access unless Internet Identity itself is recovered. This disclosure appears before creation, including on mobile. Saved credentials are encrypted document content, not Vault unlock credentials.

The dedicated canister records the creator as owner. For team access it resolves the owner by Vault ID and checks the authenticated caller’s grant. Private content/key reads are authenticated update calls. The client verifies vetKD against the network master key and the pinned header before installing a nonextractable browser root. The key input binds the Vault canister, II owner principal, Vault ID, immutable random nonce and key name. Document v 3 authenticated encryption binds that same context, document ID, revision, usage and chunk index. Sequence changes do not change the root. See [the current protocol](protocol.md).

Vault JavaScript, its canister, Internet Identity and their authorized updaters remain trusted. A compromised session signing key with a valid II delegation can exercise the owner's Vault API and derive its key; there is no independent Vault factor. AuthClient 5.0.0 requests an eight-hour delegation and uses 30-minute idle logout in the workspace, picker and embed; the UI checks validity every second even during activity. Logout deletes local SDK storage and clears private application state, but **does not revoke a retained session signing key together with its still-valid II delegation**. The replica rejects it after its signed expiry. Do not describe local sign-out, a closed tab or a client lock as server-side credential revocation.

Wiki and Vault have separate canisters, databases and origin-derived principals. Wiki saves an opaque Markdown reference to each selected document. Opening that reference in an interactive article loads a read-only Vault iframe. The canonical Vault derivation origin is `https://<vault-canister-id>.icp0.io`, with `https://vault.kinic.xyz` as its allowed application origin and `https://id.ai` as provider. Never add the Wiki origin to Vault alternative origins. The canister also serves certified `/.well-known/ii-app-metadata` (name, description, logo path) and `/.well-known/ii-app-logo.png` so Internet Identity can show Kinic Vault on its sign-in screen. Internet Identity reads these and `/.well-known/ii-alternative-origins` cross-origin, so all three carry `Access-Control-Allow-Origin: *`. Only the Vault embed route family permits framing by the canonical Wiki origin. The picker opens a separate window and checks the opener and its origin. Local HTTP configuration and root-key fetching belong only to disposable test builds. Updating Wiki does not update Vault. Use separate controller permissions where separate updater trust is required.

Creation retains one operation/Vault ID in RAM for uncertain replies. Refresh preserves that retry. If key acquisition fails after the header was created, retry opening that header instead of creating another Vault. A root is never relabelled with a changed owner/canister/Vault/nonce/key name/public key. A missing or changed target closes its private context. Close Vault keeps II signed in; Sign out clears app authentication. Switching owners or Vaults clears the previous private view and fences late callbacks.

Interrupted saves keep encrypted request bytes and their operation/upload IDs in the current session. Resume save retransmits the exact pending action. Cancel save first reconciles actual upload status, then performs bounded cleanup. Reload/lock discards the local job; the owner can list and cancel orphaned encrypted uploads. No plaintext or interrupted-save job is persisted for cross-reload resumption. Verified nonextractable root handles are retained separately in the browser device-key store. Receipt replay is guaranteed for 24 hours, not indefinitely. Exact cleanup retries replay the previous result; the next batch uses a fresh outer operation and the same cleanup job.

Fresh installations create schema 14. The backend validates and migrates the supported historical layouts: owner schemas 8, 9 and 10, grant-bearing schema 10, team schema 11, subsidy schemas 11 and 12, and combined schema 13. It retains owner headers, encrypted documents, pending-upload provenance, grants, accounting, subsidy consumption and mutation receipts. Unknown or hybrid layouts are rejected atomically. Upgrade the Vault backend before publishing either UI that calls shared or rename methods. Existing owner-only clients continue to work. Earlier binaries cannot reopen a migrated schema-14 store. A rollback requires a separately validated schema-14-compatible build; do not reinstall or downgrade the store. Retain source and Wasm provenance for each release.

Each owner can have three Vaults, 100 MiB of current plaintext per Vault, and 200 MiB of charged usage. The UI limits notes and credentials to 256 KiB and attachments to 10 MiB. History, ciphertext, pending operations and reservations also consume quota. Monitor actual stable memory and cycle headroom as usage grows. Vault uses the SQLite VFS and canister limits for physical storage.

Fresh key acquisition has bounded prepaid fallback capacity when content or ordinary receipt slots are full: 16 emergency receipts per owner, retained for 24 hours. Exact retries reuse their slot; exhaustion refuses new key operations until capacity is reclaimed. Normal key rates, execution credit and canister reserve checks still apply. The canister minimum cycle reserve is separate from the owner's prepaid balance. See [the capacity bounds](../vault-accounting-capacity.md).

Admission reserves completion capacity for each upload's chunks/commit. Admitted work can complete at the owner quota using those reservations while execution still requires credit. Owner cleanup remains available at zero credit and full capacity using resource-specific prepaid cleanup receipts. Cancellation removes one encrypted chunk per batch; document purge immediately hides retained history and fences object-ID reuse, then bounded collection reclaims ciphertext. Whole-Vault deletion physically removes its row after bounded cleanup and restores Vault capacity; IDs are never reused and no permanent Vault tombstone is kept. Timer GC persists a round-robin owner cursor through upgrade so a no-work owner cannot starve another owner's expired work.

Production funding is enabled only for the pinned KINIC ledger, with immutable pre-send search state and user-requested authoritative reconciliation. Existing account balances/journals/status and valid late settlement are preserved. The synthetic-funding Cargo feature, synthetic ledger and injected state fixtures are nondeployable testing artifacts. Unknown payments beyond retry bounds require the manual ledger scan described below; retaining a journal alone does not establish payment. Do not send replacement payments or invent compensating credit. See [accounting and capacity](../vault-accounting-capacity.md).

Lock/logout/expiry/idle/unmount clears application references, DOM, File selections, editor contents and undo history, and revokes owned Blob URLs. All three views use the same 30-minute activity timeout; hiding a view does not add a shorter timeout. JavaScript garbage collection does not guarantee physical RAM erasure. Explicit clipboard copies and downloaded plaintext files remain under the user's control. Explicit Sign out clears related Vault views within the same browser storage partition. Vault stores a random UUID in `localStorage` at `kinic-vault-logout` to distinguish older views from fresh logins. The UUID has a `pending:` prefix while the SDK removes its cached delegation. Sign-out notifications stay on the Vault origin. Each SDK client stages credential writes in memory. Browsers with Web Locks publish an accepted login to the SDK’s standard IndexedDB records and coordinate restoration with deletion. On browsers without Web Locks, new logins last for the current view and reloading requires signing in again. Local idle and delegation expiry clear that view. Browsers with Web Locks preserve the SDK delegation while another authenticated view is using it and remove it when the last view expires. II's normal SDK delegation storage is separate from the device-key database. Verified nonextractable AES-GCM root handles are saved in IndexedDB under the canister and authenticated caller, bound to the immutable owner context and public key. Closing, signing out and idle expiry retain these handles; reopening authenticates and revalidates current access before reuse. A shared member's new key request uses the owner's subsidy or credit. **Delete saved keys from this browser** deletes this caller's handles and advances a shared epoch to fence older views and in-flight writes. Access denial or a changed immutable header evicts the target Vault's handle. Persistence failure falls back to memory and a later paid retrieval may be needed. Plaintext, raw keys and DEKs must not enter persistent storage, URLs, analytics or logs. Origin code can use saved handles; signing out does not cryptographically protect them from that origin.


## Production funding and user-requested reconciliation

Production builds support ICRC-2 KINIC purchases only through ledger `73mez-iiaaa-aaaaq-aaasq-cai`. The certified configuration reports `fundingMode: production`; synthetic builds remain separately labelled and nondeployable. The controller selects the recipient and conversion rate; each accepted quote pins that configuration and a freshly obtained ledger fee. The spender is this Vault canister, not Wiki.

Before any debit, Vault durably records its ledger search start and exact transfer identity. A failed tip lookup is known-unsent and retryable. Unknown transfer outcomes retain their original amount, fee, memo and creation time; do not create a replacement payment to resolve uncertainty.

Choose a saved payment and Check ledger history to run `reconcile_purchase`. Each authenticated update processes at most100blocks, following only archive callbacks supplied by the pinned ledger. The screen runs at most10updates per click, displays progress and can stop/resume. Stopping a scan does not cancel or undo a payment. There is no periodic scanner. Confirmation atomically records Paid and credits the beneficiary once; absent, malformed or unavailable evidence leaves the payment pending.

Build backend Wasm without browser dependencies using ordinary cargo build. The distribution entrypoint scripts/build-vault-canister.sh enables embedded-assets and verifies the source-embedded build provenance, HTTP/reconciliation exports and absence of fixture exports. Production packaging rejects local-origin settings, synthetic funding and compiler-flag overrides. Local acceptance assets are separate and cannot pass this release check.

This change does not authorize production deployment, DNS changes or live-funds transfers. Main integration waits for the complete Rust/client/browser stack and its exact-commit acceptance results.

The browser prepares validated certified sign-in configuration alongside AuthClient initialization. Sign-in remains disabled until both are ready; clicking invokes SDK login immediately so popup creation retains browser user activation. Configuration failure requires a reload. Listings decrypt metadata only; typing filters titles. “Search note contents” explicitly reads note bodies transiently and keeps only matching IDs until query/list changes or session teardown. Authenticated metadata binds the complete plaintext length and chunk count.

Owners can choose **Actions for Vault → Manage members** on a Vault card to list and remove grants without opening its root or paying for a key request. The same controls remain available after a key-service failure. Adding or changing a grant remains subject to the canister’s spending and capacity checks.
