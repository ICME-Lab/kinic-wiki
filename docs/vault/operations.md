# Standalone Vault operation and upgrades

Vault assets and the dedicated Vault canister form one trusted application. A user’s browser holds recovery secrets, plaintext, unwrapped Vault keys and ephemeral signing keys in its private Session. Trust in Vault JavaScript and everyone authorized to update that JavaScript or the canister remains essential. Internet Identity authenticates the owner; origin isolation does not protect against a malicious authorized Vault update. Wiki code and its database lifecycle receive no Vault authority. Updating the Wiki canister alone does not update the Vault. Controller permissions remain explicit: anyone authorized to update both canisters is trusted for both, so use separate controller permissions when separate updater trust is required.

Configure the exact HTTPS Vault origin, its RP ID, the intended vetKD key name, the separate Vault canister and ledger before enabling writes. The certified configuration and `/.well-known/ii-alternative-origins` must agree with that origin. Never add the Wiki origin to the Vault alternative-origin list. The `same-origin-allow-popups` policy permits the strictly origin/source checked Internet Identity authorization popup; the application creates no Wiki-to-Vault session or key bridge. CSP denies framing. Local HTTP origins and root-key fetching are test-only settings.

Keep the original encrypted archive and recovery kit until the replacement is active and its saved archive has been completely verified. File reselection verifies bytes; a browser cannot certify durable backup storage. Legacy v1 archives and raw base64url recovery secrets remain readable by the independent offline recovery tool and import into fresh v2 generations. Existing archives are not rewritten in place. New v2 keys bind the canister, owner, Vault, epoch, fresh instance nonce and key name; restoring never recreates an old generation or grants global access to a recovery candidate.

Restoration alone does not revoke previously registered Global passkeys. A still-valid Global key can obtain fresh authority over the current owner’s Vaults, including the restored instance. Known compromised registrations require incident revocation, which itself requires a remaining trusted key covering all affected Vaults. A recovery candidate receives only scoped access and cannot use restoration to acquire that broader revocation authority. Disabling an old virtual test device is not evidence of server-side revocation.

During incident response, allocate every remaining target before preparing its kit and archive. Allocation uses fresh proof for the exact stored incident declaration; preparation and final atomic cutover use their distinct grants. A target replaced or removed by recovery stays terminal and its original generation is not resurrected. When every original target has been purged, the parent incident resolves by removal/replacement without a cutover digest. A separate restoration can still be pending: its guards and saved-file recovery obligations remain. When any original target remains, its completed kit, full archive verification and fresh whole-job cutover proof are still required.

Active editing past Normal grant expiry obtains fresh UV for the exact still-current generation on Save or Resume save without locking or wiping the draft. An encrypted save that has started remains one upload after a known rejection; Resume save checks its authoritative status before obtaining replacement authority. Failed or cancelled proof and Busy retain the draft. The unlocked root is bound to a copied full generation, including independent Principal bytes. A changed, missing or non-Active target immediately locks and clears private state, including for an empty Vault. An updated header cannot relabel an old root; unlock the new generation again. Unknown requests keep their exact signature and must be resolved before renewal. The browser reuses only an identical unexpired grant within the same authority phase. Explicit fresh resume and final incident cutover still request fresh proof. The server permits at most three live and six retained owner grants; completed or upgrade-invalidated grants can occupy slots through their five-minute lifetime and two-minute receipt retention. A temporary Busy result can therefore require about seven minutes before fresh authorization is admitted. Resolve any uncertain signed request first; never discard its exact retry bytes to obtain new authority. After idle logout, sign in again and resume the exact job with the required saved files. No client reuse extends the server lifetime or evicts receipts.

Interrupted ordinary saves retain only encrypted request/manifest/chunks, upload identity and phase in the current browser session. The editor and additional saves in that Vault remain disabled until Resume save finishes or Cancel save resolves the upload. Unknown signed requests are retried byte-for-byte before reconciliation or renewal. Authority expiry is handled at every chunk and commit, and a retained commit receipt can complete reconciliation even after its revision leaves readable history. Dismissing cancellation's passkey prompt before dispatch leaves the upload resumable.

Lock, identity change and reload destroy the local job. Use the interrupted encrypted-save list to cancel an upload left on the canister, then save again. This is not a cross-reload save-resume file or a browser cache. Owner-only list/status calls are authenticated updates, bounded to ten summaries per page and contain no document names or plaintext. Signed cleanup requires fresh current-generation passkey authority and remains available without prepaid credit. Cancellation persists its fence before removing at most one protocol chunk (1 MiB plus its 16-byte tag) per batch; the same cleanup job/cursor resumes after interruption or upgrade. Reserved capacity remains held until the terminal receipt replaces the upload. Commit-first cancellation preserves the published revision. Terminal receipts retain the existing 24-hour/10,000-row bounds; this is not a permanent operation-ID tombstone.

Schema v6 adds nullable `uploads.cancel_job`. Existing upload requests, digests, reservations and commit receipts survive the additive migration. Resume an old upload with fresh proof after upgrade. A v5 binary is not a downgrade/recovery target once v6 has been installed; use a corrected compatible v6 binary.

Upgrades must preserve stable storage and the current persisted transition schema. Before updating, retain source commit provenance and deployable Wasm, verify the contract and upgrade suites, and keep original/prepared backup files for interrupted recovery. Resume uncertain requests using the existing job, operation and saved target files; do not replace them with new random requests. The acceptance suite upgrades paused jobs into a compatible current binary. It does **not** authorize downgrading a current transition row into an older binary that predates the integrated schema. Old fixtures are used only for historical-to-current migration, never as a current-state downgrade or repair mechanism.

Logical quota is not physical canister memory. Ciphertext/history/pending rows, owner and Vault limits, accounting reservations and SQLite/VFS memory overhead must be monitored separately. Production funding is unavailable: default builds reject quotes and all transfer dispatch, including exact retries, before calling the ledger. Controller funding configuration cannot enable it. Existing balances, journals, status reads, quote cancellation and late authoritative callback settlement remain intact. Reviewed authoritative ledger reconciliation is an unresolved release dependency; retained evidence alone cannot recover an unknown payment. In synthetic acceptance only, funding buys execution credit, not additional storage. The empirical memory sample and its limits are documented in [validation](validation.md); it is not a worst-case physical-capacity guarantee. Unknown payment retry exhaustion and the missing authoritative reconciliation path are documented in [accounting and capacity](../vault-accounting-capacity.md).

Lock clears application references, pending operations, file selections, editor contents and undo history. Browser and JavaScript garbage collection do not guarantee physical RAM erasure. Internet Identity delegation storage is separate from Vault content storage; no plaintext, recovery secret or unwrapped Vault key belongs in Web Storage, IndexedDB, a service worker cache, URLs, analytics or logs.

The `synthetic-funding-test-only` Cargo feature is exclusively for synthetic-ledger fixtures. Its certified `/config.json` identifies `fundingMode: "synthetic-test-only"`; default binaries identify `"unavailable"`. The synthetic builder writes to `target/vault-synthetic-funding-build` with nondeployable provenance. Production-origin configuration in that fixture tests origin policy only; it does not make the artifact a deployable production binary. Never deploy it or point it at real funds. There is no runtime controller switch to remove the production funding restriction.
