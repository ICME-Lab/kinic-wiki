# Standalone II-only Vault operations

Sign in with Internet Identity, then create or select a Vault. There is no additional Vault passkey, recovery secret, backup, import or export protocol. Losing access to Internet Identity permanently loses Vault access unless Internet Identity itself is recovered. This disclosure appears before creation, including on mobile. Saved credentials are encrypted document content, not Vault unlock credentials.

The dedicated canister derives ownership from the authenticated IC caller. Private content/key reads are authenticated update calls. The client verifies vetKD against the network master key and the pinned header before installing a nonextractable browser root. The key input binds the Vault canister, II owner principal, Vault ID, immutable random nonce and key name. Document v 3 authenticated encryption binds that same context, document ID, revision, usage and chunk index. Sequence changes do not change the root. See [the current protocol](protocol.md).

Vault JavaScript, its canister, Internet Identity and their authorized updaters remain trusted. A compromised session signing key with a valid II delegation can exercise the owner's Vault API and derive its key; there is no independent Vault factor. AuthClient 5.0.0 requests an eight-hour delegation and uses five-minute idle logout; the UI checks validity every second even during activity. Logout deletes local SDK storage and clears private application state, but **does not revoke a retained session signing key together with its still-valid II delegation**. The replica rejects it after its signed expiry. Do not describe local sign-out, a closed tab or a client lock as server-side credential revocation.

Wiki and Vault have separate canisters, databases and origin-derived principals. Wiki only links to Vault. The canonical Vault derivation origin is `https://<vault-canister-id>.icp0.io`, with `https://vault.kinic.xyz` as its allowed application origin and `https://id.ai` as provider. Never add the Wiki origin to Vault alternative origins. CSP forbids framing; the II popup checks origin and source. Local HTTP configuration and root-key fetching belong only to disposable test builds. Updating Wiki does not update Vault. Use separate controller permissions where separate updater trust is required.

Creation retains one operation/Vault ID in RAM for uncertain replies. Refresh preserves that retry. If key acquisition fails after the header was created, retry opening that header instead of creating another Vault. A root is never relabelled with a changed owner/canister/Vault/nonce/key name/public key. A missing or changed target closes its private context. Close Vault keeps II signed in; Sign out clears app authentication. Switching owners or Vaults clears the previous private view and fences late callbacks.

Interrupted saves keep encrypted request bytes and their operation/upload IDs in the current session. Resume save retransmits the exact pending action. Cancel save first reconciles actual upload status, then performs bounded cleanup. Reload/lock discards the local job; the owner can list and cancel orphaned encrypted uploads. No plaintext or decrypted root is persisted for cross-reload resumption. Receipt replay is guaranteed for 24 hours, not indefinitely. Exact cleanup retries replay the previous result; the next batch uses a fresh outer operation and the same cleanup job.

Fresh installations create complete schema 7. Schemas 1–6, foreign and incomplete stores are rejected without modifying their stable bytes. Current schema 7 upgrades preserve content, pending uploads, reservations, accounting, journals and receipts. No legacy migration or downgrade is supported. Upgrade only to a compatible reviewed binary after retaining source and Wasm provenance and checking current acceptance results. A current-schema fixture proves resumed pending ciphertext decrypts to the original bytes after an upgrade and a fresh vetKD open.

Each owner can have 3 Vaults,100 MiB current plaintext per Vault and 200 MiB charged owner usage. The canister also has a shared 200 MiB logical ceiling, including its 16 MiB prepaid accounting pool. Notes/credential content are limited to 256 KiB and attachments to 10 MiB in the UI. History, ciphertext, pending operations and reservations also consume capacity. These logical limits are not a physical-memory guarantee. SQLite's 262144-page ceiling at 16 KiB/page is 4 GiB.

Fresh key acquisition has bounded prepaid fallback capacity when content or ordinary receipt slots are full: 64 emergency receipts globally and 16 per owner, retained for 24 hours. Exact retries reuse their slot; exhaustion refuses new key operations until capacity is reclaimed. Normal key rates, execution credit and canister reserve checks still apply. The canister minimum cycle reserve is separate from the owner's prepaid balance. See [the capacity bounds](../vault-accounting-capacity.md).

Admission reserves completion capacity for each upload's chunks/commit. Admitted work can complete at full shared logical capacity using those reservations while execution still requires credit. Owner cleanup remains available at zero credit and full capacity using resource-specific prepaid cleanup receipts. Cancellation removes one encrypted chunk per batch; document purge immediately hides retained history and fences object-ID reuse, then bounded collection reclaims ciphertext. Whole-Vault deletion leaves a permanent tombstone. Timer GC persists a round-robin owner cursor through upgrade so a no-work owner cannot starve another owner's expired work.

Production funding remains compiled-disabled. Controller settings cannot enable quotes or ledger transfers. Existing account balances/journals/status and valid late settlement are preserved. The synthetic-funding Cargo feature, synthetic ledger and injected state fixtures are nondeployable testing artifacts. Authoritative ledger reconciliation remains an unresolved production release dependency; unknown payments beyond retry bounds are not recovered by retaining a journal. Do not send replacement payments or invent compensating credit. See [accounting and capacity](../vault-accounting-capacity.md).

Lock/logout/expiry/idle/unmount clears application references, DOM, File selections, editor contents and undo history, and revokes owned Blob URLs. Hidden private sessions close after one minute. JavaScript garbage collection does not guarantee physical RAM erasure. Explicit clipboard copies and downloaded plaintext files remain under the user's control. II's normal SDK delegation storage is separate from Vault roots, DEKs and plaintext; those Vault secrets must not enter persistent browser storage, URLs, analytics or logs.
