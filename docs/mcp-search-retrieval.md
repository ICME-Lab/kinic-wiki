# MCP retrieval search

The optional retrieval pipeline combines up to three keyword searches and reranks twenty short candidate excerpts with Jev. `search` retains its existing input/output schema, default limit of 10, and maximum limit of 20. Body reads (`read_paths` / `fetch_many`) remain limited to 10. Search does not prefetch full pages into the Worker.

## Configuration and activation

| Setting | Default | Effect |
|---|---|---|
| `MCP_SEARCH_RERANK_ENABLED` | unset / disabled | Only the exact value `true` enables retrieval search. |
| `TYPESAFE_API_KEY` | unset | Required when enabled; missing/blank keys select legacy search. |

Checked-in deployment configuration leaves the feature disabled. This implementation does not provision secrets or deploy. When separately authorized, upgrade the canister first, deploy the Worker with the feature disabled, verify the effective production CPU limit, configure the existing Jev credential, and then enable the flag. Disable the flag to restore legacy search without a canister downgrade or data migration. Use the repository's official `cf` deployment workflow.

With the flag enabled, public and private searches send the original question, candidate paths, and at most 512 UTF-16 units of body excerpt per candidate to the existing Jev service. User identity, OAuth tokens, and full page bodies are not sent. The requesting user's canister permissions apply to every search. Logs contain counts, timings, HTTP status and fixed failure codes, without questions, paths, excerpts or credentials.

Explicit `preview_mode: none` or `content-start`, questions over 512 UTF-16 units, disabled configuration and missing credentials use legacy search. The usual Light preview remains the model-facing search preview; the new reranking excerpt is internal and is not added to the MCP output schema. Returned scores and match reasons remain the canister's original values; result order can change.

Private MCP requests with a routed bearer token are streamed to the existing session-scoped `McpAuthStateV5` Durable Object. That object checks the token, origin, expiry and scopes and runs the MCP handler with a request-local identity and actor. No delegation is returned to the entry Worker. OAuth endpoints and public MCP retain their existing entry path. This keeps certificate verification and the retrieval pipeline out of the private entry Worker's 10 ms CPU budget; it does not eliminate their CPU or Durable Object duration usage. No new namespace or storage migration is required.

Agents reuse only certificate-verified public node keys, partitioned by endpoint and current trust root, for at most five minutes and sixteen cache entries in total. Query signatures are still checked on every response. The SDK invalidates and refreshes keys on verification failure. Tool schemas are constructed once; servers, handlers and identities remain request-local.

MCP servers share an Ajv schema validator, avoiding repeated validator initialization. The SDK patch also reuses Candid field-label hashes, with at most 512 entries and labels of at most 128 UTF-16 units. This cache contains schema labels, not document contents or identities. The hash algorithm, numeric field IDs, wire format and signature verification are unchanged.

The Candid patch reads signed LEB128 integers directly from the input cursor. The upstream implementation copies the entire remaining message while inspecting each integer, including unrelated page bodies. The replacement preserves signed values, sign extensions and the reader checkpoint on malformed input without those copies. Both installed SDK versions and module formats use the patch. SDK 6 is used by this repository's Node / `nodejs_compat` servers and additionally hashes byte strings of at least 16 KiB with synchronous native `node:crypto` SHA-256. The hash and signature algorithms are unchanged. SDK 5.4 browser clients retain the portable JavaScript hasher; the version-specific patches are pinned separately. The SDK 6 query transport also releases its owned CBOR input buffer after successful decoding when `ArrayBuffer.transfer` is available. The pinned CBOR decoder copies byte strings, so signature verification still reads the complete independent Candid payload. An ownership regression test protects this assumption when dependencies change; malformed CBOR retains the original diagnostic behavior.

## Canister contract

`search_nodes_for_retrieval` is an additive query. Its request contains `database_id`, `query_text`, `intent`, optional `prefix`, and `top_k` (1–20). The query and intent each accept at most 512 UTF-16 units. The response is `Result<vec { hit: SearchNodeHit; rerank_excerpt: text }, text>`.

`intent` is the original question for all auxiliary searches. Each result preserves the existing Light hit. The additional excerpt scans only the first 40,000 UTF-16 units, removes the experiment's metadata/citation scaffolding, and selects an earliest best-scoring window of at most 512 units at stride 256. It never splits a surrogate pair. NUL and embedded BOM are preserved; leading/trailing whitespace and BOM follow the frozen experiment's JavaScript trim behavior.

The existing search candidate and permission code is shared. Light content anchors retain their existing full-body lookup when necessary. Path hits only load a bounded byte prefix for the new excerpt, using BLOB substring so SQLite does not stop at embedded NUL. Each hit's content is read once for both previews. Storage schemas and existing search interfaces are unchanged.

## Limits and failures

The Worker retrieves 20 hits for the original query, generates up to two distinct auxiliary queries from the original Light hits, and runs those two concurrently with one request-scoped actor. It combines ranks, deduplicates paths, selects 20 candidates by the frozen lexical score, and sends one Jev request. No retry is added to this retrieval actor or to Jev.

The new query's CBOR response is limited to 256 KiB before Candid decoding. The candidate path/excerpt JSON is limited to 32,000 UTF-8 bytes; the actual Jev request and response are each limited to 64 KiB. Oversized candidate payloads skip Jev. Jev has a one-second timeout; failures return the pre-Jev candidate order. An auxiliary query failure discards that query's hits. Initial authorization/network failures remain tool errors. Only the replica's explicit missing-method rejection permits fallback to legacy `search_nodes`.

The shared Jev helper retains its default of five selections and its existing short-list bypass. MCP explicitly requests up to twenty selections and reranking even for short lists. Other consumers keep their current behavior.

The existing final MCP tool-result limit remains 256,000 UTF-8 bytes. Size checks now count UTF-8 bytes without allocating a second encoded buffer, and oversized metadata still produces an explicit size error. The outer JSON-RPC envelope is not included in this tool-result limit.

For `read_node` and `read_nodes`, the MCP Candid text adapter validates the entire UTF-8 body with native `node:buffer.isUtf8` and decodes only the bounded byte prefix needed for the 40,000 UTF-16-unit display limit plus truncation detection. Signature verification still covers the complete original wire response. The adapter changes neither the Candid wire type nor metadata; malformed UTF-8 in an omitted tail still fails decoding.

Batch body responses admit metadata in input order, calculate the escaped UTF-8 contribution directly from each original body and its Unicode-safe clipping boundary, and construct display text and structured content only after choosing the final body budget. The final serialized size is checked independently. This avoids rebuilding the full response for every binary-search step. Requests that already fit use their maximum permitted body budget. The ten-path limit and existing metadata, Unicode and truncation behavior are preserved; no session queue is introduced. Database groups within one body-read request are consumed sequentially so eight concurrent requests cannot open 32 near-limit body responses at once. This trades cross-database latency for bounded simultaneous wire allocations; the ten-reference limit and input order are unchanged.

## Verification

- `pnpm --dir workers/wiki-mcp test` and `typecheck`: existing and new contracts, failure modes and worker tests.
- `pnpm --dir packages/jev-reranker test` and `typecheck`: shared-helper compatibility, 1/10/20 selections, request/response limits.
- `pnpm --dir workers/wiki-mcp test:retrieval`: offline replay through Rust excerpt generation and the production Worker pipeline. Requires Cargo, no provider credential.
- `pnpm --dir workers/wiki-mcp test:retrieval:live`: repeats the 46 public cases with actual Jev calls using the existing root `.env.local` credential. This deliberately refreshes `evaluation/recorded-jev.json`; inspect that diff. It never edits wiki pages.
- `pnpm --dir workers/wiki-mcp bench:retrieval`: macOS Miniflare/workerd resource measurement, full private HTTP/OAuth/DO path with SDK signature verification enabled, fixture-controlled canister and model responses. The local replica serves real BLS certificates and Ed25519 query signatures; corrupted signatures/certificates must fail before measurement. Saves `.tmp/resource-results.json`.
- `pnpm --dir workers/wiki-mcp bench:retrieval --cpu-study --delegated`: CPU measurements for 1/10/20 results and eight concurrent requests, plus separate V8 profiles. Every serial condition records 40 individual samples; its 10 ms gate checks the maximum, including first requests and integrity checks. Parallel conditions report batch averages; individual CPU under concurrency is explicitly unmeasured and receives no per-request pass. `--direct` runs the handler outside the session DO; add `--uncached` to disable public-key reuse for comparison. `--focused` limits the cases, and `--reverse` reverses their order. `--edge-process` measures forwarding in a separate local workerd process, connected by a test HTTP bridge to the real OAuth/DO/SDK backend. This isolates forwarding cost but is not Cloudflare's deployment topology or billed CPU. The delegated fixture restores an encrypted test delegation; it does not perform live Internet Identity login or renewal. Results and profiles are ignored under `evaluation/.tmp/`; `WIKI_MCP_BENCH_OUTPUT_DIR` can select a separate output directory. Run profiler-summary and budget regression tests with `node --test workers/wiki-mcp/evaluation/cpu-study.test.mjs`.
- `pnpm --dir pocketic-tests test:wiki-retrieval`: builds diagnostic and production Wasm and checks actual queries and instruction counts in PocketIC. `POCKET_IC_BIN` may select an installed PocketIC binary. The production Wasm excludes the diagnostic query.

For CPU experiments, run `node workers/wiki-mcp/evaluation/benchmark-worker.mjs --delegated --paired --paired-final` from the repository root. This compares the pre-optimization baseline, field-label caching plus shared Ajv, and an additional experimental JSON Schema cache, alternating their order in one process for 40 samples per condition. Omitting `--paired-final` screens all five candidates. `--cpu-study --delegated --screen --experiment=candid,ajv` runs one candidate combination; `--experiment=baseline` reconstructs the baseline. These switches change only the evaluation bundle. Without experiment switches the benchmark measures the installed product. Results are written to the ignored `.tmp/paired-experiments.json` or `.tmp/cpu-study-results.json`. Avoid concurrent benchmarks when comparing CPU results.

For large body reads, run `node workers/wiki-mcp/evaluation/benchmark-worker.mjs --delegated --reads-only --read-parallel=4`. Compare 1, 2, 4 and 8 parallel requests; 8 runs 104 requests including memory sampling. The fixture enforces the canister's 1,000,000-byte batch budget using Candid-encoded item sizes and reserved framing. Its default near-limit case returns nine pages and one size error; add `--read-scenario=tenpages` to exercise ten successful pages. Add `--read-scenario=multidb` for ten different databases, each returning a 980–1,000 kB Candid response, via the public `fetch_many` tool. The eight-parallel run makes 104 MCP requests and 1,040 signed body queries. Add `--multiple-sessions` to spread requests across eight independent OAuth sessions and delegations. The suite verifies complete-body signature rejection, tampered-body rejection, key rotation without query replay, input order, etags, BOM/NUL/Unicode preservation, both MCP body representations and truncation flags. The default mixed suite also includes this multi-database case. All body cases verify per-item errors and the final MCP size limit. `largestCombined` records heap plus backing storage from the same sample, not the sum of separate maxima. Search and body-read cases must stay within the local 96 MiB sampled-memory and 50 ms average process-CPU gates; parallel per-request CPU remains unmeasured.

Add `--read-stages` for a separate diagnostic run with receive, decode and format checkpoints. Those checkpoints pause only the evaluation bundle to obtain heap samples, so their timings are not production timings. Ordinary benchmarks do not install the checkpoints. `--read-profile` records a separate CPU diagnostic after the unprofiled measurements; it does not affect the measured workload counters. The CPU experiment baseline disables field-label caching and Ajv reuse only; other product fixes, including the signed-integer decoder, remain active in every condition.

The replay fixture contains 46 labeled cases from public Hono documentation and Dom's Brain posts. Retrieval relevance is not answer correctness or verification of the posts' claims. The fixture and recordings contain no provider credentials. Temporary bundles/results are ignored under `evaluation/.tmp/`.

Local CPU measurements are OS process counters including workerd/DO activity, not Cloudflare's billed isolate CPU. Heap and backing storage are sampled separately from CPU and are not proof of a production memory maximum. Query waits are fixture-controlled in the resource benchmark; live provider latency is measured by the accuracy runner. Production plan/CPU settings must be checked before enabling the feature.

The signed benchmark leaves the production VFS client and SDK unchanged. Its local `/status` supplies a test root; `/read_state` supplies a root-signed subnet delegation and subnet-signed node-key certificate. Every search request creates a fresh agent. The certificate chain is verified on cache misses, and query signatures are always verified. Before measurement the fixture checks corrupt certificates, corrupt query signatures and node-key rotation. Counters assert that warm searches reuse public keys while every query remains signed; no certificate fetching is expected during warm-cache trials.
