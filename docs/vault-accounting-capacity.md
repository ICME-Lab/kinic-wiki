# Dedicated Vault accounting capacity

The dedicated Vault reserves **16 MiB within its shared 200 MiB logical limit** for private prepaid accounting. This reservation exists even when there are no accounts. Vault content, retained history, uploads, exports and other control state share the remaining 184 MiB, including the existing global overhead. Owner storage billing continues to use owner content/control usage; the fixed accounting reservation is not charged to each owner and creates no credit.

`global_capacity` is an aggregate read-only query returning `used`, `limit`, `accounting_reserved`, `legacy_excess`, `overcommitted` and `overage`. It allocates no account or owner namespace. Owner `get_quota` remains separate: a low owner usage can coexist with shared exhaustion. The shell should show the accounting reservation and shared exhaustion from this query (the shell integration is a separate UI task).

| Accounting state                              | Maximum rows | Maximum logical bytes per row |
| --------------------------------------------- | -----------: | ----------------------------: |
| Prepaid accounts                              |        1,024 |                           512 |
| Payments, including unresolved receipts       |        1,024 |                         4,096 |
| Fee lookup leases                             |            8 |                         4,096 |
| Cycle reservation/checkpoint journal          |       10,000 |                           512 |
| Disposable accounting audit                   |       10,000 |                           512 |
| Global accounting settings and billing cursor |        Fixed |                  65,536 total |

These upper bounds total **15,056,896 bytes**, leaving **1,720,320 bytes** inside the 16 MiB reservation. A whole logical row counts each string/blob as a four-byte length plus UTF-8/raw bytes and each scalar, including nullable integers, as eight bytes. Repeated SQL wallet/operation columns count in addition to serialized JSON. SQLite indexes/pages, stable-memory VFS and transient Wasm heap are independent physical measurements; this is not a physical-memory cap.

Settings use seven prepaid slots of at most 8,192 bytes per whole key/value row, plus one prepaid 512-byte billing cursor (57,856 bytes total). The current keys are `config`, `funding`, `generation`, `quote_fee_serial`, and `cleanup-budget`. The last key holds the global zero-balance cleanup budgets. Scalar widening and replacement of these existing rows need no new slot, including during upgrade and callbacks. Two slots remain for bounded incident/restore metadata. Any future key must fit a free slot; extending/repartitioning these bounds must keep the total within 64 KiB, preserve existing protected values, and provide its migration tests. Adding a key does not expand the accounting pool.

Before ledger transfer, admission counts the union of existing accounts and distinct beneficiaries of InFlight/Unknown payments. Different pending payments to the same absent beneficiary share one future account slot. A definitive failure releases only its own membership. Unknown and orphaned in-flight requests retain membership, including through upgrade; exact retries preserve all pinned transfer arguments. Account credit and payment completion are one transaction. Existing accounts can top up at the account limit **when a payment-record slot is available**. New quotes fail before fee/transfer calls when the payment budget or the narrower wallet limit (16) is full. No arbitrary read or invalid request allocates a zero-balance account.

Whole-row guards run before inserts and updates. Transfer admission also checks every maximum-width typed callback receipt before a debit is possible. External ledger error messages are discarded; only the existing bounded typed status is saved. The audit discards oldest historical evidence before insertion, in the same transaction. Payment receipts and reservation/checkpoint journals retain exactly-once settlement authority independently of that audit. Positive balances, Unknown payments, unsettled reservations and unbilled checkpoints are never evicted for admission. A full reservation journal rejects new work while existing refunds, settlement, checkpoints and authenticated cleanup reuse existing rows, including at zero or tiny balance.

The fixed 16 MiB is the current-version prepaid floor. Exceptional legacy state adds a separately reported conservative `legacy_excess` to global used bytes, within the unchanged 200 MiB limit. Count excess above each declared limit is charged at its whole-row upper bound; encoded bytes beyond each whole-row bound are added too. Account commitments count the union of persisted accounts and distinct pending absent beneficiaries, so a confirmed callback replaces an already charged future row and cannot suddenly increase excess. Settings use the seven slot/8 KiB row bounds and prepaid cursor described above. This deliberately conservative legacy measure does not consume the pool's spare bytes first and does not measure physical memory. Normal current-version admissions have zero legacy excess; future audit/receipt slots remain fully prepaid.

Upgrade installs guards without rebuilding or deleting old tables. Previously admitted account/pending-beneficiary commitments remain valid even when their legacy union exceeds 1,024; they may settle, while new distinct beneficiaries are blocked. A pre-production database above the new global allowance initializes normally and reports overcommitment. Ciphertext reads, encrypted export and authorized bounded cleanup remain available; growth is rejected until usage is reduced. Export reuses one finished/aborted/expired snapshot slot for that same owner and Vault; an active unexpired snapshot remains protected. Replaced inactive export IDs no longer carry a replay receipt; their snapshots no longer pin revisions.

Unknown payments beyond the 23-hour retry window or 100-attempt bound remain durable pending manual authoritative reconciliation. There is no automatic reissue, unsafe controller credit, or new reconciliation tool in this change. No intermediate Vault database has been deployed to production; legacy offline v1 archive import remains separate.
