作成日: 2026-10-15。計画の提案であり、実装着手・公開の承認を示さない。

## 1. 目的と判断基準

一度設定すれば短いコマンドで通常利用でき、動かないときは原因と次の操作が分かり、実行後は実際に残った証跡を確認できるようにする。継続学習基盤のモデル、検索、文脈組み立て、評価、公開の判断は変えない。

利用者の基本動線は次とする。

```sh
kinic-vfs-cli agent setup --engine codex
kinic-vfs-cli agent doctor --engine codex
kinic-vfs-cli agent run --engine codex --task "修正してテストする"
kinic-vfs-cli agent recall --task "認証まわりの過去の判断を調べる"
kinic-vfs-cli agent status
```

setupには明示した書き込みがある。doctorには読み取り通信があり得る。run/recallには既存の実行・検索・記録動作がある。statusは既定でローカル参照だけとする。

成功は設定項目の網羅性ではなく、次の三点で判断する。

1. 設定済みプロジェクトでrunner/recall JSONを毎回指定せずに動く。
2. 失敗時に設定・認証・DB・エンジン・フックのどこを確認すべきか分かる。
3. 文脈提供、評価、公開の観測事実と証跡へ辿れる。記録・提供だけを採用や性能向上と表示しない。

## 4. A: 設定の一本化

### 保存する情報

既存の `.kinic/config.toml` と既存のユーザー設定を拡張する。

| 領域 | 内容 |
| --- | --- |
| 既存の接続項目 | replica_host、canister_id、database_id。既存の意味と優先順位を維持 |
| learning | 既存RecallOptionsに対応する検索条件、文脈予算、状態保存先 |
| agents.codex / agents.dsh | 既存RunnerConfigに対応する実行先、モデル、推論設定、上限など |

task、run_id、receipt、候補ID、contexts、実行結果は設定に含めない。APIキーを保存しない。embeddingの認証などは環境変数名を参照する。既存runner JSONの明示的なenvironment指定は互換性を保つが、setupで秘密値をTOMLへ取り込まない。

初版では新しいプロファイル継承機構やevaluation設定を追加しない。評価のsuite・試行数・出力は従来の明示指定を維持する。モデル等の未指定値は、エンジン固有の既存の解決規則を維持し、setupで推測した値を固定しない。

### 解決規則

- 学習・エンジン設定はフィールド単位で「明示CLI値 → 明示した既存JSONの値 → プロジェクト設定 → ユーザー設定 → 基点の既定値」。明示JSONのデシリアライズ時に埋まる既定値を、利用者の明示値と誤認しない。
- 既存JSONだけで実行していた場合、基点と同じ有効設定になることを互換試験で固定する。相反する旧来の既定値がある場合は、この互換性を優先し、変更を隠さず説明する。
- `--engine` とrunner JSONのengineが矛盾したらエラーとし、別エンジンへ自動切り替えしない。runではengineかrunner-fileを明示する。既定エンジンの新設は初版に含めない。
- `--cwd` を対象コマンドで共通化し、対象ディレクトリからプロジェクトを探索してから設定・接続を解決する。フックはイベントのcwdを渡す。サブディレクトリ探索・Git境界の規則は既存の接続探索に揃える。
- 新TOML内の相対パスは、その値を定義した設定ファイルの親ディレクトリ基準。単純な実行ファイル名はPATH検索、明示的なパスは設定ファイル基準。CLI指定パスと旧JSON内パスは既存の解釈を維持し、実装前にテストで固定する。
- 接続設定の引数・環境変数・設定ファイル間の優先順位は変更しない。
- 有効な値の取得元を内部表現に保持する。秘密値を除いた設定と取得元をdoctorから確認できるようにする。
- 不正な設定を黙って既定値へ置き換えない。通常実行は説明付きで失敗し、doctorは可能な範囲の診断を続ける。

### 実装責務

設定解決はRustの共有処理を正本とし、既存のRunnerConfig/RecallOptionsへ変換する。Python/JavaScriptにTOMLの優先順位処理を複製しない。両フックは既にCLIを呼んでいるため、その呼び出しで解決し、設定解決のための追加プロセスは常用経路に増やさない。

Codex側の現行「recall JSONがなければCLIを呼ばない」判定は、新TOML設定でも利用できるようにする。再送先を識別するbindingも新設定に対応させる。DB・identity・プロジェクトの変更後に、過去のキューを新しい接続先へ送らない。

database link/unlinkとsetupは対象キーだけを更新する。未知のテーブル、無関係なキー、可能な限りコメントを保持する。unlinkでは学習設定だけ残るファイルを削除しない。

## 5. A: setup

`agent setup --engine codex|dsh` を共通入口とし、既存codex setup/dsh setupは互換入口として同じ生成・更新処理を呼ぶ。

- 未設定時は必要な最小設定と配布物を生成する。既存設定と同じなら変更しない。
- 変更が必要な既存設定には差分と対象パスを表示する。既定では上書きせず、`--apply` の明示でその変更を適用する。未知の設定を削除しない。`--dry-run` は全対象について書き込みを行わない。
- DSHの実行先は明示指定を優先する。未指定ならPATH上の候補を列挙し、候補が曖昧な場合は選択を要求する。候補を確認目的で起動せず、ラッパーも内容や存在の確認に留める。
- マシン固有の実行パスは、保存先未指定ならユーザー設定へ保存し、対象パスを出力する。プロジェクト設定への保存は明示選択にする。既にプロジェクト側に実行先がありユーザー設定を上書きする場合は、その優先順位を表示する。有効にならないユーザー設定を追加してsetup成功とはせず、必要な変更差分を示す。この既定動作は本改訂案での設計判断とする。
- Codexは配布物の配置、外部アプリへの登録、有効化・信頼設定、再起動、実際の観測を別項目で報告する。配置だけでreadyと表示しない。
- DSHは配布物とoverlayの準備までを初版の範囲とし、利用者の既存プロファイルへの導入・起動は別の操作として案内する。
- 最後に対象engineのdoctorコマンドを表示する。setupはモデル実行・DB作成・Wiki書き込み・再送を行わない。

## 6. A: doctor

```sh
kinic-vfs-cli agent doctor
kinic-vfs-cli agent doctor --engine dsh --json
kinic-vfs-cli agent doctor --strict
```

engine省略時は設定済みエンジンを診断し、未設定なら共通項目と設定方法を表示する。全エンジンの設定を強制しない。

確認対象は設定解決と取得元、実行ファイルの存在・実行属性、ローカルで確認可能な認証情報の有無、DBへの読み取り、読み取りで確認可能な必要API、配布物の配置、保存先の状態。外部実行ファイルは通常doctorでは起動せず、`--version` にも頼らない。DB確認の通信はタイムアウトを設ける。

| 判定 | 意味 |
| --- | --- |
| ok | この項目を裏付ける確認ができた |
| warning | 動作上の注意や劣化条件が確認できた |
| error | 必要条件の不足または明確な失敗を確認した |
| unknown | 権限・方式・証跡などが足りず判断できない |
| skipped | 前提不足または対象外のため確認しなかった |

設定、認証、DB権限、API未対応、通信失敗は別の安定した判定コードを持たせる。API未対応と判定するには根拠を必要とし、タイムアウトをAPI未対応や権限不足に変換しない。書き込み権限は読み取りだけで確定できなければunknownとする。

実行ファイルが存在してもモデル接続は未確認。認証情報の存在は認証成功の証明ではない。フックが存在しても有効化や動作は未確認。保存先は作成や試し書きをせず、静的な確認で書き込み可否を断定しない。

JSONにはschema_version、checked_at（UTC）、対象、設定の取得元、checks（項目ID、status、code、根拠、対処方法）を含める。キー・トークン・environmentの値・生の外部エラー本文は出さず、安全な項目だけを構造化する。項目の失敗は他項目の結果を消さない。

終了コードは、errorなしで0、診断対象の問題で1、結果を組み立てられないなど診断自体の失敗で2。通常warning/unknownは0、strictでは1。skippedは前提不足を表す項目の判定に従い、対象外だけでは失敗にしない。

通常doctorは推論、埋め込み生成、Wiki書き込み、DB/ディレクトリ作成、再送、修復、キャッシュ更新を行わない。接続・identityの初期化前にローカル診断を開始できる構造にする。

## 7. B: 最小status

通常statusは既存ローカル成果物を読み取る。新しい全体状態機械は作らない。

- 対象プロジェクト、DB、identityの識別情報、設定済みエンジン、設定取得元。
- 最終ローカル記録と、確認できる最終送信成功・失敗。
- CLI outboxとCodex再送キューの件数を別々に表示。共通イベントIDで照合できない場合は合計を出さない。
- 最後の文脈receiptと対応run。文脈の組み立てと、エンジンへ実際に渡した観測を区別する。
- ローカルで確認できる最新の候補・評価・公開・ロールバックへの参照。リモート全件を把握しているように表示しない。

各表示に観測日時、取得元、参照ID/パス、確認範囲を付ける。値がない場合も「未実行」「失敗」「未確認」を証拠なしに混同しない。公開済みでも品質向上を証明したとは表示しない。

SQLiteは既存ファイルを読み取り専用で開く。Outbox::open等、ディレクトリ・DB作成やマイグレーションを行う経路を流用しない。存在しない保存先は未確認として返す。読み取りロック・破損でも取得可能な他項目を表示する。

## 8. C: 追加の判断条件

### probe

静的doctorでは解決できない起動・モデル応答問題が残る場合に追加する。`agent doctor --engine ENGINE --probe` だけが実際のエンジンを起動する。課金を伴い得ることをヘルプで明示する。

所有する短い専用セッション・作業領域で応答・終了を検証し、既存セッションには接続しない。基点のrunnerを使い、Codex JSONL/DSH sdkの方式を維持する。タイムアウト・出力上限・子プロセス終了・学習フックの抑止を検証する。probeが通常の成功実績・学習候補に混入しないようにする。

結果を保存する場合は通常診断と分離した小さな証跡にし、engine、実行先、モデル、対象プロジェクトなどの設定識別子を含める。設定変更後の過去成功を現設定の成功に流用しない。

### status --refresh

他マシン・リモートの結果を確認する必要が出た場合に追加する。読み取りのみで正本を照会し、確認日時と範囲を表示する。接続失敗時にはローカル証跡を残して古さを明示する。キャッシュ保存や索引作成は行わない。

### 観測索引

既存成果物だけでは必要な照合ができないと判明した場合に限り追加する。run_id、receipt_id、candidate_id、evaluation_id、publication_idと既存証跡への参照を中心にし、業務状態やcanisterの正本を複製しない。再構築可能にし、status自体が作成・修復しない。

## 9. 実装順序と検証

### Aの順序

1. 基点の有効設定・旧JSON・接続優先順位・フック再送bindingを互換試験で固定する。
2. 追加キーを保持する設定更新と共有resolverを実装する。
3. run/recall/hookをresolverへ接続し、cwdを含む通常利用を成立させる。
4. setupを共通化し、DSH実行先と外部導入の案内を整える。
5. ローカル診断を先に実行できるdoctorを実装する。
6. ヘルプ・導入文書を更新し、受け入れ試験を行う。

### 必須の受け入れ試験

| 分類 | 確認すること |
| --- | --- |
| 設定 | 明示値・旧JSON・プロジェクト・ユーザー・既定値の組み合わせ。部分上書きと矛盾したengine |
| パス | サブディレクトリ、別プロジェクトへのcwd、各設定ファイル基準のパス、空白を含む実行先 |
| 更新 | link/unlink/setup後も未知テーブル・無関係な設定が残る。dry-run/差分のみでは変更なし |
| 互換 | 従来のrunner/recall JSONが使え、有効設定と既存のパス解釈が変わらない |
| フック | TOMLだけで両エンジンが利用できる。設定・DB切替後に古いキューを別接続先へ送らない |
| 診断 | 実行先欠落、認証不足、明確な権限拒否、API未対応、タイムアウトを区別。identity不足でも他項目を返す |
| 副作用 | 外部起動、推論、埋め込み、書き込み、再送がゼロ。診断前後で対象ファイル・DBの内容と存在が変わらない |
| 表示 | 配置だけで有効化済み・動作済みとしない。秘密値を設定・エラー経由でも出さない |
| 出力契約 | JSONスキーマ、安定した判定コード、通常/strictの終了コード |

Bには追加で、通信失敗・再送・応答消失の証跡、キューの二重集計回避、文脈提供と採用の区別、公開・ロールバックの既知範囲、保存先未作成・破損・ロック時の非破壊性を検証する。Cのprobeには専用セッション所有権、終了処理、通常記録からの分離を必須にする。

### 性能・意味の維持

同じDBスナップショット、identity、検索入力、embedding応答、エンジン設定を固定し、旧JSON経路と新TOML経路について以下を比較する。

- 解決後のRunnerConfig/RecallOptionsと実際の起動引数・環境上書き方針。
- 検索要求、選択したノードと版、文脈本文と予算処理。receiptの日時・生成IDは比較から分離する。
- 評価モード、suite、試行数、公開条件。今回の簡便化が評価の既定値へ波及しないこと。
- 既存の関連Rust/Python/DSHテスト。常用フックの追加プロセス数と設定解決時間。

実モデルの結果は確率的なので完全一致を完了条件にしない。既存の比較評価を保持し、1回のsmokeを品質向上の証拠にしない。元の継続学習基盤に残る広いheld-out反復評価という公開条件を、この改善で解除しない。
