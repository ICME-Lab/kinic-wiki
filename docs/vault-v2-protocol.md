# Vault v2 foundation protocol

Task 5 implements the generation, authentication, mutation and portable-format foundations. The resumable incident/restore transitions belong to Task 7; complete browser workflow wiring belongs to Task 8. This intermediate build deliberately rejects the old unsigned write/key-release routes. It is not a release-ready replacement for those workflows.

## Generation and cryptography

`vault_types::Generation` and `vault-crypto/src/generation.ts` define the same byte encoding. Variable fields have a four-byte unsigned big-endian length prefix. The encoding is: sized `kinic-vault/generation/v2`, one byte `2`, sized canister principal bytes, sized owner principal bytes, 16-byte content VaultID, eight-byte big-endian epoch, 32-byte server nonce, sized UTF-8 key name. Epochs cannot exceed SQLite's signed 64-bit range.

The vetKD input is `kinic-vault/key-input/v2` followed by those generation bytes; its canister context is `kinic-vault/kek/v2`. The browser verifies against the configured trusted master and expected canister, then derives `kinic-vault/vrk-wrap/v2`. The returned public key is not a trust anchor.

V2 root/DEK AAD consists of individually sized `kinic-vault/envelope/v2`, generation bytes, original object ID, big-endian revision/epoch, and purpose (`normal`, `recovery` or `dek`). Wrapper version chooses the AAD explicitly. Metadata and chunk ciphertext retain the v1 AAD and ciphertext. Every document save still creates a fresh DEK; rewrapping changes only the DEK envelope.

Recovery signing seeds are HKDF-SHA256 with zero 32-byte salt and info `kinic-vault/recovery-proof/ed25519/v2`. The Ed25519 signature domain is `kinic-vault/recovery-proof/v2\0`. The service checks its server-persisted binding against the current header's verifier and full source identity. Candidate or archive-supplied verifiers do not authorize a live reset. Task 7 must persist and validate the exact recovery ceremony before calling that helper.

## Signed mutation transport

The exact wire schema is generated from Rust into `crates/vault_types/mutation.did`, with JS/TS bindings generated by the existing contract script. `mutate(payload, signature)` verifies Ed25519 over `kinic-vault/mutation/v2\0 || payload`. Candid decoding has byte/type/decoding/skipping limits and rejects trailing input; no Rust reserialization is used for signature verification.

Each grant binds the caller, canister, ephemeral public key, current credential revocation version, exact generations, purpose, runtime/configuration fence and fixed five-minute expiry. One next counter and one exact-byte digest/result are retained. Same previous counter plus identical bytes returns the cached result. Other replay or concurrent work fails. Synchronous effects and the receipt commit in one transaction. Asynchronous work first commits its handle and receipt; retries never repeat external calls. A subsequently signed `KeyResult` retrieves completion. An upload commit returns compact revision metadata; use the existing owner read route to retrieve its manifest/chunk hashes.

The browser `SignedMutations` retains exact bytes/signature across ambiguous transport failure and blocks the next mutation until retry resolves. Its signing key is memory-only and destroyed by `Session.lock`.

The legacy public protected mutation routes return `Unauthorized`. Funding/configuration routes retain their separate existing authority. Owner ciphertext/header/export reads remain available. A new namespace bootstrap is allowed only when no existing namespace/vault/credential can be taken over. Its independent private cleanup seed and public generation nonce come from separate `raw_rand` calls.

## Capacity and cleanup

There are at most three live/six retained normal grant rows per owner and 256 live/512 retained globally. Expired grant receipts survive the five-minute expiry plus the 120-second callback deadline. Namespace creation prepays six grant slots, ten physical credential slots, candidate/bootstrap/ordinary ceremony slots, owner control/authority state, and a separate 64 KiB cleanup slot. Reusing a grant/credential slot does not release its permanent capacity. These charges are in the Vault owner/global 200 MiB content budget.

Each retained nondeleted revision prepays two 2 KiB wrapper/control slots (maximum wrapper payload 1 KiB per slot), including their bounded identity/digest/index overhead. Schema version 3 creates the two-slot wrapper table. Task 7 supplies staged-overlay publication and effective read/export selection; no inactive wrapper is silently used now.

Cleanup has one pending ceremony, one active grant/last receipt and one job cursor in its independently prepaid 64 KiB slot. HMAC-SHA256 under the private namespace seed binds the canister, owner, immutable namespace/targets, checked serial, issue/expiry times, configuration/runtime fence, requested job and ephemeral public key. Challenge TTL is 120 seconds. Fresh remaining-passkey UV is mandatory. Replacement revokes the old cleanup grant; current-job status is owner-readable.

Daily limits are 100/1,000 owner/global challenges, separately 100/1,000 proof attempts, and 1,000/10,000 signed cleanup verification attempts. Invalid WebAuthn and Ed25519 proofs count in a separate committed admission transaction. Exhaustion returns `RateLimited { retry_after }`; it never asks for purchased cleanup credit. Successful batch/cursor/receipt changes are atomic. Cleanup payloads are at most 8 KiB and result receipts at most 4 KiB.

Purge freezes the exact target set, cancels/settles only its eligible existing flights, then deletes at most one 1 MiB ciphertext chunk or one content/control row per batch. Accounting recovery handles at most one key flight and one orphan challenge in the same transaction. It never refunds submitted key cost, clears another live target's flight, or starts new external work. Namespace authentication remains until all targets and unsettled accounting are gone; replay retention finishes before recreation. The owner financial serial high-water mark, prepaid account and payment journal survive namespace recreation; a new seed/identity is allocated.

Automatic expired-data cleanup does not delete pinned history. The II-only exception is an exact never-activated pending attempt with no registered credential; it cannot purge an Active instance. Missing seeds/generations fail closed.

## Compatibility and remaining boundary

`KVLT0002` headers contain full portable generation identity, v2 envelopes and recovery verifier. The authenticated footer includes the complete header and exported effective records. The independent archive reader and CLI still read v1 without altering its KDF/AAD. `transformArchive` fully validates the source archive and all AEADs, creates fresh root/kit, rewraps every retained DEK, validates the target archive, and returns a separately computed target restore commitment. It preserves content IDs, revision sequences and payload ciphertext.

Existing v1 canister rows have no implicit v2 authority. This migration does not invent a nonce, cleanup seed or recovery verifier for legacy live data. There is no deployed legacy database requiring an online conversion. Task 4 funding/account state survives the schema upgrade independently.

A pre-existing accounting-budget gap remains separate from this implementation: `content::global_usage` does not count private `accounts`, `payments`, `quote_fee_flights`, `account_ledger` or `vault_cycle_reservations`. Some journals have their own row limits, but the global 200 MiB content calculation is not a combined accounting/database size attribution. Before claiming whole-database full-quota acceptance, add a bounded accounting-control pool/admission hook and durable-account/journal retention bounds without evicting unsettled work. The SQLite page cap remains independent.

The accounting-control capacity gap above is explicitly scheduled as Task 6. Incident/restore is Task 7, complete UI Task 8 and final acceptance Task 9.
