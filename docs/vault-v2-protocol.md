# Vault v2 foundation protocol

Task 5 implements the generation, authentication, mutation and portable-format foundations. The resumable incident/restore transitions belong to Task 7; complete browser workflow wiring belongs to Task 8. This intermediate build deliberately rejects the old unsigned write/key-release routes. It is not a release-ready replacement for those workflows.

## Generation and cryptography

`vault_types::Generation` and `vault-crypto/src/generation.ts` define the same byte encoding. Variable fields have a four-byte unsigned big-endian length prefix. The encoding is: sized `kinic-vault/generation/v2`, one byte `2`, sized canister principal bytes, sized owner principal bytes, 16-byte content VaultID, eight-byte big-endian epoch, 32-byte server nonce, sized UTF-8 key name. Epochs cannot exceed SQLite's signed 64-bit range.

The vetKD input is `kinic-vault/key-input/v2` followed by those generation bytes; its canister context is `kinic-vault/kek/v2`. The browser verifies against the configured trusted master and expected canister, then derives `kinic-vault/vrk-wrap/v2`. The returned public key is not a trust anchor.

V2 root/DEK AAD consists of individually sized `kinic-vault/envelope/v2`, generation bytes, original object ID, big-endian revision/epoch, and purpose (`normal`, `recovery` or `dek`). Wrapper version chooses the AAD explicitly. Metadata and chunk ciphertext retain the v1 AAD and ciphertext. Every document save still creates a fresh DEK; rewrapping changes only the DEK envelope.

Recovery signing seeds are HKDF-SHA256 with zero 32-byte salt and info `kinic-vault/recovery-proof/ed25519/v2`. The Ed25519 signature domain is `kinic-vault/recovery-proof/v2\0`. The service checks its server-persisted binding against the current header's verifier and full source identity. Candidate or archive-supplied verifiers do not authorize a live reset. Task 7 must persist and validate the exact recovery ceremony before calling that helper.

## Signed mutation transport

The exact wire schema is generated from Rust into `crates/vault_types/mutation.did`, with JS/TS bindings generated by the existing contract script. `mutate(payload, signature)` verifies Ed25519 over `kinic-vault/mutation/v2\0 || payload`. Candid decoding has byte/type/decoding/skipping limits and rejects trailing input; no Rust reserialization is used for signature verification.

Each grant binds the caller, canister, ephemeral public key, current credential revocation version, exact generations, purpose, runtime/configuration fence and fixed five-minute expiry. One next counter and one exact-byte digest/result are retained. Same previous counter plus identical bytes returns the cached result. Other replay or concurrent work fails. Synchronous effects and the receipt commit in one transaction. Asynchronous work first commits its handle and receipt; retries never repeat external calls. A subsequently signed `KeyResult` retrieves completion. An upload commit returns compact revision metadata; use the existing owner read route to retrieve its manifest/chunk hashes.

The browser `SignedMutations` retains exact bytes/signature across ambiguous transport failure and blocks the next mutation until retry resolves. Its signing key is memory-only and destroyed by `Session.lock`.

The legacy public protected mutation routes return `Unauthorized`. Funding/configuration routes retain their separate existing authority. Owner ciphertext/header/export reads remain available. A new namespace bootstrap is allowed only when no existing namespace/vault/credential can be taken over. Its independent private cleanup seed and public generation nonce come from separate `raw_rand` calls.

## Capacity and cleanup

There are at most three live/six retained normal grant rows per owner and 256 live/512 retained globally. Expired grant receipts survive the five-minute expiry plus the 120-second callback deadline. Namespace creation prepays six grant slots, ten physical credential slots, candidate/bootstrap/ordinary ceremony slots, owner control/authority state, and a separate 64 KiB cleanup slot. Reusing a grant/credential slot does not release its permanent capacity. These charges are in the Vault owner/global 200 MiB content budget.

Each retained nondeleted revision prepays two 2 KiB wrapper/control slots (maximum wrapper payload 1 KiB per slot), including their bounded identity/digest/index overhead. Schema version 3 creates the two-slot wrapper table. Task 7 supplies staged-overlay publication and effective read/export selection; no inactive wrapper is silently used now.

Cleanup has one pending ceremony, one active grant/last receipt and one job cursor in its independently prepaid 64 KiB slot. HMAC-SHA256 under the private namespace seed binds the canister, owner, immutable namespace/targets, checked serial, issue/expiry times, configuration/runtime fence, requested job and ephemeral public key. Challenge TTL is 120 seconds. Fresh remaining-passkey UV is mandatory. Replacement revokes the old cleanup grant; current-job status is owner-readable.

An existing Global credential can obtain the narrow `CancelCreation` cleanup purpose for a never-activated pending creation, including before nonce publication or after a session lock. It binds the public namespace identifier (a one-way domain-separated hash of the independent private seed), exact VaultID and immutable creation operation. It permits only `Cleanup/CancelSetup` for that attempt, clears matching random-flight authority, and never authorizes derive, Active purge or ordinary writes. A nonce arriving between challenge, proof and mutation does not invalidate this exact-attempt cancellation; phase Pending and sequence zero are rechecked at each boundary. Once a cancellation batch commits, its namespace/VaultID/creation-attempt marker fences all Normal-grant issuance, effects, callbacks and cached key replay for that exact attempt, even while accounting keeps cleanup incomplete. Both generation-bound Cleanup/CancelSetup and CancelCreation use the same marker. Cleanup renewal/continuation and separate grants for unrelated instances remain available; completed cancellation retains terminal receipt replay. Unfinished setup status exposes the public identifier, never the seed.

Daily limits are 100/1,000 owner/global challenges, separately 100/1,000 proof attempts, and 1,000/10,000 signed cleanup verification attempts. Invalid WebAuthn and Ed25519 proofs count in a separate committed admission transaction. Owner counters survive namespace reclamation/rebootstrap in the retained owner control row; only UTC day rollover resets them. Exhaustion returns `RateLimited { retry_after }`; it never asks for purchased cleanup credit. Successful batch/cursor/receipt changes are atomic. Cleanup payloads are at most 8 KiB and result receipts at most 4 KiB.

Purge freezes the exact target set, cancels/settles only its eligible existing flights, then deletes at most one 1 MiB ciphertext chunk or one content/control row per batch. Accounting recovery handles at most one key flight and one orphan challenge in the same transaction. It never refunds submitted key cost, clears another live target's flight, or starts new external work. Namespace authentication remains until all targets and unsettled accounting are gone; replay retention finishes before recreation. The owner financial serial high-water mark, prepaid account and payment journal survive namespace recreation; a new seed/identity is allocated.

Automatic expired-data cleanup does not delete pinned history. The II-only exception is an exact never-activated pending attempt with no registered credential; it cannot purge an Active instance. Missing seeds/generations fail closed.

## Compatibility and remaining boundary

`KVLT0002` headers contain full portable generation identity, v2 envelopes and recovery verifier. The authenticated footer includes the complete header and exported effective records. The independent archive reader and CLI still read v1 without altering its KDF/AAD. `transformArchive` fully validates the source archive and all AEADs, creates fresh root/kit, rewraps every retained DEK, validates the target archive, and returns a separately computed target restore commitment. It preserves content IDs, revision sequences and payload ciphertext. V1 source restore roots keep the zero-32-byte seed and original record leaf algorithm. V2 target roots start with `SHA256("kinic-vault/restore-root/v2\0" || generationBytes)` and then chain `SHA256(previous || restoreLeaf(record))`. Thus empty and tombstone-only targets commit to the complete fresh generation. The v2 archive reader and store restore validator use that same seed.

Existing v1 canister rows have no implicit v2 authority. This migration does not invent a nonce, cleanup seed or recovery verifier for legacy live data. There is no deployed legacy database requiring an online conversion. Task 4 funding/account state survives the schema upgrade independently.

A pre-existing accounting-budget gap remains separate from this implementation: `content::global_usage` does not count private `accounts`, `payments`, `quote_fee_flights`, `account_ledger` or `vault_cycle_reservations`. Some journals have their own row limits, but the global 200 MiB content calculation is not a combined accounting/database size attribution. Before claiming whole-database full-quota acceptance, add a bounded accounting-control pool/admission hook and durable-account/journal retention bounds without evicting unsettled work. The SQLite page cap remains independent.

The accounting-control capacity gap above is explicitly scheduled as Task 6. Incident/restore is Task 7, complete UI Task 8 and final acceptance Task 9.


## Incident completion and root-envelope compatibility (Tasks 8–9)

Live v2 normal/recovery root envelopes bind the zero object ID and revision **zero** in `generationAAD(g, ZERO, 0n, purpose)`. The generation bytes already bind epoch and nonce. DEK envelopes bind their actual object/revision. Newly emitted portable v2 headers carry `envelope_revision: "0"`; the archive footer authenticates this field with the rest of the header. For compatibility, an existing v2 archive with this field absent uses its generation epoch in the root-envelope AAD. The reader accepts only canonical `"0"` or the exact canonical generation epoch, rejects malformed/other values and v1 misuse, and never tries a second AAD after decryption fails. V1 KDF/AAD remains unchanged. This discriminator is offline format information, never server authority or permission to replace a live verifier. Restore and new browser setup must use the live revision-zero convention and explicit field when producing new v2 archives.

Task 9 stages at most 100 ordered retained revisions per signed batch. The immutable source snapshot includes available history for deleted objects; tombstones advance both commitments without wrapper rows. Canonical effective source manifests are hashed, including the currently published overlay after a prior rotation. Counts, cursors, chained source/target commitments and one retry digest occupy the existing prepaid transition summary. Wrapper insertion uses the inactive one of the two prepaid slots. Before a subsequent incident needs an occupied inactive slot, signed `ClearInactive` performs bounded 100-row cleanup under a current ordinary grant.

`IncidentPrepareExport` fixes one exact job/attempt/export descriptor, new header and target commitment in the transition slot. Read requests bind the descriptor digest obtained from encrypted owner status, so reusing an expired export ID cannot revive the old read capability. Owner-II queries may then retrieve that descriptor, effective target manifests and original chunks without maintenance, storage billing updates, acknowledgment, key release or implicit export preparation. These reads reject wrong owner/job/attempt/export/descriptor digest, reset/cancellation/terminal purge, descriptor expiry and completed cutover. Source ciphertext export remains available during the freeze. Its saved flag changes only source backup metadata, not target verification or writability. Cutover atomically aborts source exports admitted during the freeze so an old descriptor cannot mix with the new published wrapper slot.

The client saves and reselects the new archive and kit, verifies the full authenticated footer and every DEK/metadata/chunk AEAD, compares the exact target header and target commitment, then signs the exact descriptor/commitment/archive hash/length/verifier/post-cutover sequence acknowledgment. Save callbacks represent user acknowledgment, not browser attestation of durable external storage. An already verified acknowledgment remains durable after its read descriptor expires; new prepared reads or a new export require a new descriptor and invalidate the old backup acknowledgment.

A separate `IncidentCutover { job, digest }` grant requires fresh WebAuthn UV over the complete verified job, including explicit Purged audit entries. Publication requires all remaining targets verified and no Purging/Cancelling/Cancelled entry. One transaction updates headers, wrapper pointers, current scoped credential source-nonce to target-nonce mappings and backup sequences, and completes the job. Old/job grants then fail current-state validation. No record scan or payload copy occurs at finalization. Owner-II `incident_status` retains `completed_digest` after grant invalidation, so an ambiguous final response is resolved through status rather than another mutation. Restarts preserve the irreversible source freeze and the exact unfinished cancellation cleanup binding; reset/cancel discard staged descriptors, coverage and acknowledgments before bounded inactive-slot cleanup.

## Scoped restore admission (Task 10)

Task 10 implements admission and its storage/authority boundary. Target allocation, destructive replacement, import, new-kit and target-backup verification, activation, and exact restore cancellation are deferred to Task 11. The dedicated real restore/full-quota acceptance follows in Task 12. An `Admitted` status is not a grant and cannot derive a key, mutate a Vault, register Global authority, or activate a target.

The existing prepaid 64 KiB `transition` setting now has a versioned container for the incident parent and at most one restore admission child. The decoder also reads historical untagged Task 9 incident statuses. Unknown versions, missing tagged fields, malformed admission phases and invalid parent linkage fail closed. Admission limits the existing container to 32 KiB and initial combined state to 48 KiB; candidate public credential JSON is at most 8 KiB. Every final combined serialization remains bounded by 64 KiB. There is no second owner job slot. Incident status queries still return only the parent.

`initialize_restore_namespace(operation)` can initialize an empty funded owner's private namespace seed through one durably reserved, paid and fenced random call. It returns the seed's domain-separated public namespace identity and creates no header, target-generation nonce, credential or key. The initialization marker prevents legacy bootstrap or empty-namespace reclamation from replacing this restore-only namespace. Existing namespaces reuse their identity.

`begin_restore_admission` binds the source archive digest, length, commitment and crypto-source identity to the exact namespace/Vault/attempt/job. These are client-supplied source identifiers, not server AEAD validation. A live collision independently captures the current registered generation and recovery verifier. The candidate then completes `register_restore_candidate` with UV registration and `prove_restore_candidate` with a separate UV possession assertion binding its key digest and exact pending job. None attestation alone is insufficient. For a live collision, `prove_restore_current` also requires a strict signature under the captured CURRENT registered verifier; the server rechecks it against the live header. The returned `recovery_message` contains the exact bytes to sign, including the recovery-proof domain. Do not prepend that domain a second time. Archive verifier and candidate possession alone never authorize replacement.

The candidate remains in the transition record and receives no credential row, authority entry or `GrantInfo`. Ten occupied physical credentials reject admission; nine plus one pending candidate is allowed. No automatic eviction or same-key reuse optimization is implemented. Existing pending creation/restoration/purge and conflicting cleanup are rejected before admission. One nested admission may reference only an exact frozen source of its immutable incident parent; all source pins and the parent's original audit remain unchanged.

`restore_admission_status` is an owner-only read available without a key or compatible configuration. `resume_restore_admission` preserves the candidate and exact job but requires fresh possession and, for collisions, fresh current-verifier proof. The stored phase records previous progress; its challenge expiry and runtime/configuration fence still govern proof validity. Upgrades invalidate old proof without erasing durable status. Generic owner changes, semantic configuration changes, incident mutations, owner GC, namespace reclamation and generic cleanup are conservatively blocked while admission is pending. Task 11 must add exact child cancellation/settlement and replacement consumers before relaxing these guards; there is no II-only Active purge exception.

The pure `transformArchive` helper accepts a separate current-live generation for replacement and chooses checked `max(archive epoch, current live epoch) + 1`. Without one it retains checked source epoch + 1. Source archive identity may differ from the target namespace; current-live and target owner/canister/Vault must match and their nonces must differ. This is local format validation, never server authorization. The explicit-zero v2 root-envelope convention and legacy fieldless-v2/v1 readers remain unchanged.
